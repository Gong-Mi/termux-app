## 一、核心前提变更

### 1.1 不上架、不分发、自用为主

| 原假设 | 更新后 |
|--------|--------|
| 需通过 Google Play / F-Droid 审核 | **不需要** |
| 权限数量需克制以避免用户恐慌 | **不需要** |
| APK 体积需控制在合理范围 | **不需要**（但仍建议理性控制） |
| 不能使用 ProtectedPermissions | **可以使用**（root/系统环境下） |
| 需兼容厂商 ROM 的严格限制 | **只需兼容目标设备** |

**结论:** 所有因"上架合规"而产生的约束全部解除。权限、体积、隐藏 API 反射、ProtectedPermissions 都不再是障碍。

### 1.2 Android 版本目标

| 指标 | 当前值 | 状态 |
|------|--------|------|
| minSdk | 28 (Android 9) | ✅ 已满足 |
| targetSdk | 35 (Android 15) | ✅ 已设置 |
| compileSdk | 36 (Android 16 Beta) | ✅ 已设置 |
| NDK | 29.0.14206865 | ✅ 已设置 |

**Android 15 特有适配检查:**

| Android 15 变更 | 当前状态 | 风险 |
|----------------|---------|------|
| 前台服务类型声明 | ✅ `FOREGROUND_SERVICE_SPECIAL_USE` + `PROPERTY_SPECIAL_USE_FGS_SUBTYPE` | 无 |
| 预测性返回手势 | ✅ `enableOnBackInvokedCallback="true"` | 无 |
| 私密通知（Private notifications） | ❓ 未检查 | 低 |
| **16KB 页面大小支持** | ❌ **未配置** | **中-高** |
| `sharedUserId` 废弃警告 | ⚠️ 仍在使用 | 低（功能正常，只是日志警告） |

**16KB 页面大小风险说明:**
- Android 15 开始，部分设备（如 Pixel 8/9、未来旗舰）使用 16KB 内存页（传统为 4KB）
- 所有 native `.so` 库必须按 16KB 对齐 ELF 段，否则 `dlopen()` 会崩溃
- NDK r28+ 默认处理，但你的 NDK 是 r29，**理论上应该已支持**
- **但 Rust 编译的 `.so` 需要确认**: `cargo-ndk` / `rustc` 是否传递了正确的 linker flags
- 检查方法: `llvm-readelf -l libtermux_rust.so | grep LOAD` 看 `ALIGN` 是否 >= 0x4000 (16384)

**建议:** 在 CI 或本地构建后，加入 16KB 对齐检查脚本。

## 二、子窗口需求的重新定义

### 2.1 原始误解 vs 真实意图

| 我的原始理解 | 用户的真实意图 |
|-------------|---------------|
| 把 Termux:API/Boot/Widget 等插件改成子窗口 | **在终端内运行 Linux 桌面/图形应用，以子窗口形式显示** |
| 解决插件签名和 sharedUserId 问题 | **解决终端与图形桌面的视觉共存问题** |

### 2.2 "终端运行桌面"的场景

### 2.3 技术路径评估（在"不上架"前提下重新评分）

不上架彻底改变了子窗口方案的可行性：

| 原障碍 | 不上架后 |
|--------|---------|
| 权限太多被 Play 拒绝 | 不存在 |
| APK 体积太大用户不装 | 不存在 |
| 焦点冲突导致终端不可用 | **仍然存在**（体验问题） |
| Widget/Boot 技术不可能窗口化 | **仍然存在**（Android 系统限制） |
| 后台启动 Activity 被系统拦截 | **可用 SYSTEM_ALERT_WINDOW 绕过** |

**结论:** 在不上架前提下，子窗口方案从"不推荐"提升为"有条件可行"。核心障碍从"合规"变成了"纯技术实现"。

---

### REQ-008: 终端内图形渲染表面（桌面/X11 支持）

**目标:** 在 Termux 终端内部提供一块图形渲染区域，用于显示 X11/Wayland 客户端或 Linux 桌面。

**可能的技术路径:**

| 路径 | 说明 | 复杂度 |
|------|------|--------|
| **A. SurfaceView 嵌入** | 在 TerminalView 旁边/上方放置一个 SurfaceView，由外部 X11 服务器渲染 | 中 |
| **B. TextureView + Skia** | 复用现有的 Skia/Vulkan 管线，把 X11 帧数据作为 texture 贴到终端 canvas 上 | 高 |
| **C. 独立 Freeform Activity** | 启动一个独立的 Activity 作为"桌面容器"，以自由窗口运行 | 低 |
| **D. 集成 termux-x11 协议** | 与现有的 Termux:X11 项目协议兼容，接收其渲染输出 | 中 |

**推荐路径:**
- 短期: **C（Freeform Activity）** — 最简单，利用 Android 原生多窗口
- 中期: **D（termux-x11 协议兼容）** — 复用社区生态
- 长期: **A/B（内嵌 Surface）** — 真正的"终端里跑桌面"体验

**优先级:** P2（列入评估，不阻塞基础架构）

---

### REQ-009: 虚拟键盘/快捷键浮动面板

**目标:** 在终端上方提供一个可拖拽的浮动工具栏，包含：
- Ctrl / Alt / Tab / Esc 等修饰键快捷按钮
- 常用符号（|、>、$、` 等）
- 可自定义的宏按钮

**技术路径:** `WindowManager.addView()` 或 `PopupWindow`。

**优先级:** P2（自用体验优化）

## 五、关键决策点

### 决策 1: 16KB 页面大小

**问题:** 是否需要立刻验证和修复？

**背景:**
- 目前只有 Pixel 8/9 和未来旗舰可能使用 16KB 页面
- 大多数 Android 15 设备仍然是 4KB
- NDK r29 应该已默认处理对齐

**建议:** 在下一个构建中加入检查脚本，如果不对齐再加 linker flag。不需要阻塞其他开发。

### 决策 2: 终端内桌面的技术路径

**问题:** 走 Freeform 独立窗口（简单）还是内嵌 Surface（复杂）？

**建议:**
- 如果目标是"在大屏/平板/DeX 上同时看到终端和桌面" -> **Freeform** 足够
- 如果目标是"在手机小屏上，终端和桌面叠加/切换" -> 需要 **内嵌 Surface**
- 可以先做 Freeform 验证概念，再做内嵌

### 决策 3: 插件架构是否动刀

**问题:** 在不上架、多用户路径修复后，现有插件 APK 是否还有问题？

**建议:** 等 REQ-001 完成后，实际测试多用户安装场景。如果每个用户能独立安装并使用插件，**就不要动插件架构**，把精力集中在终端性能和桌面体验上。
